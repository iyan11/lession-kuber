# KubeLab Desktop

Отдельное приложение для Windows x64: изучение Kubernetes и Minikube через встроенную консоль с подсказками. Знание Docker предполагается; отдельных уроков Docker нет. Интерфейс и семь практических уроков — на русском. Приложение работает локально, без аккаунтов и внешнего AI API.

## Запуск приложения

Сборка: `release/KubeLab-Setup-0.1.0-alpha.2-x64.exe`. Это установщик с мастером подготовки компонентов. Для тренажёра Docker не нужен. WSL, Minikube и kubectl находятся внутри; Docker Desktop скачивается отдельно по выбору пользователя. Сборка не подписана.

Из исходников с Node.js 22.12+:

```powershell
npm install
npm start
```

Сборка Windows x64: сначала `npm run fetch:offline`, затем `npm run build:win`. Версии зависимостей зафиксированы в package.json и pnpm-lock.yaml; для точного воспроизведения используй `pnpm install --frozen-lockfile`. Для разработки подходит `npm install`.

## Два режима консоли

- **Тренажёр** включён по умолчанию. Поддерживает конкретные команды семи уроков, моделирует кластер в памяти, не запускает процессы и не открывает порты. Это упрощённая модель: переходы состояния мгновенные, полная история ревизий и полный синтаксис CLI не моделируются. `reset` возвращает начальное состояние тренажёра.
- **Реальные команды** запускают установленные `docker.exe`, `minikube.exe`, `kubectl.exe` от текущего пользователя. Вывод поступает постепенно, stdout и stderr различаются цветом, показывается код завершения. Здесь команды действительно создают и меняют контейнеры и ресурсы Kubernetes.

Это консоль запуска CLI, а не полный PowerShell/PTY: один процесс за раз; без конвейеров, перенаправлений, переменных оболочки, `-it` и интерактивных редакторов. Поддерживаются длительные `port-forward`, `logs -f`, `get --watch`. Кнопка «Стоп» или Ctrl+C в поле ввода завершает выполняемый процесс; при закрытии окна процесс тоже завершается. Один запуск ограничен 15 минутами. Команды с JSON patch передаются напрямую в CLI без shell-интерполяции.

Встроенные команды: `help`, `clear`, `history`, `reset`. ↑↓ — история текущей сессии; Tab дополняет введённый префикс до команды курса. Команды уроков вставляются в поле по нажатию, выполнение — по Enter.

Подсказки основаны на известных шаблонах ошибок: отсутствующий образ, остановленный Docker, отсутствующий профиль, занятый порт, CrashLoopBackOff, опечатка minicube. Ошибки синтаксиса подсвечиваются при вводе. Это локальные правила; приложение не делает вид, что знает причину любой ошибки.

## Подготовка Windows для реального режима

1. Установи Docker Desktop с WSL 2 backend. Включи аппаратную виртуализацию, выполни требования установленной версии Docker Desktop. Если WSL ещё нет: `wsl --install` в PowerShell администратора, затем перезагрузка при необходимости.
2. Запусти Docker Desktop и выбери **Linux containers**. Встроенный Kubernetes Docker Desktop для этого стенда не нужен.
3. Установи Minikube и kubectl из официальных источников. Через winget: `winget install -e --id Kubernetes.minikube` и `winget install -e --id Kubernetes.kubectl`. После установки перезапусти приложение, чтобы обновился PATH.
4. Для профиля курса выделяется 2 CPU и 3072 МБ памяти. Нужна дополнительная память для Windows/Docker и место для образов; ориентируйся также на актуальные системные требования официальной документации.
5. В приложении выбери рабочую папку с Dockerfile и каталогом k8s. По умолчанию это исходный проект при разработке или вложенная папка resources/lab в сборке.

Запускай команды из обычного Windows-окружения. Не смешивай kubeconfig Windows и WSL в рамках одного урока.

## Что изучаем

1. Minikube, Docker-драйвер, Node и профиль.
2. Подготовка образа внутри Minikube, namespace, Deployment и Pod.
3. Service, EndpointSlice, port-forward и ограничения туннеля.
4. Реплики и восстановление после удаления учебных Pod.
5. ConfigMap, окружение и необходимость пересоздания Pod.
6. Rolling update, история и откат через изменение APP_VERSION.
7. Ошибка образа, Events, describe, logs и восстановление.

Урок отмечается после правильного ответа и ручного подтверждения практики. Это самооценка, а не автоматическая проверка реального кластера. Прогресс хранится в localStorage приложения на этом компьютере. История команд и вывод не сохраняются между запусками.

## Само приложение как учебный workload

В проекте есть отдельный небольшой HTTP-сервер без внешних runtime-зависимостей. Его можно контейнеризировать и развернуть в Minikube. В Docker/Kubernetes отображается браузерная версия тренажёра; запуск команд компьютера из HTTP-сервера не предоставляется.

```powershell
docker build -t kubelab:1.0 .
minikube start -p kubelab --driver=docker --cpus=2 --memory=3072
minikube image load kubelab:1.0 -p kubelab
kubectl --context kubelab apply -f k8s/lab.yaml
kubectl --context kubelab -n kubelab rollout status deployment/kubelab --timeout=120s
kubectl --context kubelab -n kubelab port-forward service/kubelab 8081:80
```

Либо из обычного PowerShell: `./scripts/Start-Lab.ps1`. Если политика выполнения блокирует скрипт, выполняй команды выше вручную. Адрес: http://localhost:8081. Туннель должен оставаться запущенным. Он направляет запросы в один выбранный Pod и не показывает балансировку между репликами.

`GET /api/runtime` возвращает имя Pod (Downward API), namespace, APP_VERSION, LAB_MESSAGE, uptime и число запросов данного процесса. `GET /healthz` и `/readyz` используются probes. `/readyz` проверяет готовность этого простого сервера; внешних зависимостей у него нет. Счётчик запросов не персистентен и сбрасывается при рестарте.

Локально HTTP-версию можно запустить командой `npm run web` на http://127.0.0.1:3000.

## Остановка и уборка

```powershell
# Остановить профиль, сохранить ресурсы
minikube stop -p kubelab
# Удалить учебный профиль вместе с ресурсами (при необходимости)
minikube delete -p kubelab
# Удалить дополнительный учебный контейнер, если запускал его вручную
docker rm -f kubelab-web
```

Все команды Kubernetes в курсе явно указывают контекст kubelab; namespaced-команды указывают namespace kubelab. `minikube start` может поменять активный контекст kubeconfig. Нельзя запускать учебные эксперименты на production-кластере.

## Разработка и проверки

`npm test` — проверка границ CLI-аргументов, прохождения курса в модели, подсказок и реального HTTP API. `node --check server.mjs` — проверка синтаксиса сервера.

Desktop использует Electron с sandbox/contextIsolation и без Node.js в renderer. IPC разрешает только конкретные операции из локального окна приложения. Внешняя навигация блокируется; ссылки официальной документации открываются отдельно. Встроенный HTTP-сервер не содержит API выполнения команд.
